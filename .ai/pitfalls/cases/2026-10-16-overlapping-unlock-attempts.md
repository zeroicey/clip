# 两次解锁重叠：后失败的那次会把已经成功的凭据擦掉

**Severity:** 🔴 high（页面进入「看起来对、其实错了」的状态，而且很难复现）
· **First hit:** 2026-10-16（真浏览器验证，间歇性，约 1/3 的运行会出现）
· **Hits since:** 0

## 症状

对着线上跑 `scripts/verify-clip-browser.cjs`，间歇性失败：

```console
FAIL  the right password reveals the content  — 这份剪贴板已经设了密码，输入密码继续。
    debug: stranger state = {"state":"locked","hidden":true,"body":"","msg":"这份剪贴板已经设了密码，输入密码继续。"}
```

也就是：**输入正确的密码之后，页面先解锁、然后把自己重新锁上**，正文被清空。
服务端日志把经过写得很清楚（同一后缀）——两次 unlock 相隔 **1 毫秒**：

```text
16:06:37.589 401  POST /api/clips/<sfx>/unlock     ← 错密码
16:06:37.590 200  POST /api/clips/<sfx>/unlock     ← 对密码
16:06:37.671 401  GET  /api/clips/<sfx>            ← 随后一个「没有凭据」的轮询
```

## 根因

页面把「当前口令」放在一个模块级变量 `password` 里，而**每个** unlock 的失败分支都会把它重置：

```js
password = storedPw();     // 失败时回到「存着的那一个」
```

两次尝试重叠时（双击、或 Enter 之后又点一下、或者纠正错密码时手快）：

1. 正确的那次：`password = pw`，请求在飞；
2. **过期的那次**响应先回来 → 它的失败分支执行 `password = storedPw()` ——
   此时 storage 还是空的（赢家还没写），于是**把刚被接受的口令擦成了空串**；
3. 赢家的响应回来 → 解锁成功 → `startPolling()` → 轮询用**空凭据**发出去 →
   服务端（正确地）回 `401` → 页面的 401 分支切回锁壳并清空正文。

用户看到的是「解锁成功了，然后又自己锁上了」。

## 修复

**每次尝试带一个 generation，只有最新那次能改页面状态**（`internal/clip/page.html`）：

```js
var gen = ++unlockGen;
...
if (gen !== unlockGen) return;      // 有更新的尝试接管了，这个响应已经是历史
```

过期响应**什么都不做**：不写 `password`、不写状态文案、不切视图。
顺带修掉了同一族的第二个症状：成功的解锁现在会清掉上一次留下的「密码不对。」——
之前会出现「正文明明已经显示出来了，旁边还挂着密码不对」。

## 守卫

`scripts/verify-clip-browser.cjs`：

- 错密码那一步现在等**终态**（`text.length > 0 && !text.includes("解锁中")`），
  而不是等「非空」——「解锁中…」是同步写进去的，等非空就等于**故意**并发发起下一次尝试。
  这个测试写法本身是让 bug 藏了很久的原因：它制造了重叠，却把结果当成随机失败。
- 新增断言：**成功解锁后 `lockstatus` 必须为空**（不能一边显示内容一边显示错误）。

## 一句话

> 客户端里「当前凭据」这种**单值状态**，在多请求重叠时必须有 generation/epoch 保护；
> 否则失败分支的**清理动作**会迟到执行，把赢家刚建立的状态抹掉 ——
> 而失败方向的后果是「自己把自己锁上」，看起来像玄学。
