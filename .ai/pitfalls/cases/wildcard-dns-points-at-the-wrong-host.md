# 泛解析的 A 记录打错了一个数字（81 而不是 8）

**症状**：hcyj 的 `*.hcyj.xyz` 号称已经泛解析，于是照常加子域名、加 Caddy 站点块。
结果 `https://clip.hcyj.xyz/` 无响应，Caddy 日志里是 ACME 校验失败。

## 根因

| 名称 | 权威 A 记录 |
| --- | --- |
| `hcyj.xyz`、`api.hcyj.xyz` | `8.148.233.134` ✅（阿里云广州，就是 hcyj） |
| `clip.hcyj.xyz`、任意随机子域 | **`81.148.233.134`** ❌（多了一个 `1`） |

两个公共解析器（`223.5.5.5`、`1.1.1.1`）给出一致结果，所以不是本地缓存；
`:80` 与 `:443` 都 TCP timeout；从 hcyj `ping 81.148.233.134` 通但 **216ms**（异地机房）——
也就是说那**不是** hcyj，是另一台机器。

## 后果为什么严重

`api.hcyj.xyz` 一直在下发 `Strict-Transport-Security: max-age=63072000; includeSubDomains; preload`。
`includeSubDomains` + `preload` 意味着浏览器对 **`*.hcyj.xyz` 强制 HTTPS 且不允许"继续访问"**。
所以子域名在**拿到有效证书之前**对外公布，访客看到的是一次硬失败（`NET::ERR_CERT_AUTHORITY_INVALID`
之类，且无法点过），而不是可以忽略的警告。

**顺序因此是硬的**：先修 DNS → Caddy 才能签发证书 → 才能对外公布。

## 修复

在阿里云 DNS（NS 是 `dns7/dns8.hichina.com`）把 `*` 的 A 记录改成 `8.148.233.134`。
**本机与 hcyj 上都没有 `aliyun` CLI 或 `~/.aliyun` 凭据**，所以这是必须由人类完成的动作。

改完后重启一次 Caddy 让它立即重试（否则要等它的退避计时）：

```bash
docker restart caddy
```

## 守卫 / 判据

- 加任何子域名之前，先 `dig +short <子域>` 并**与已知正确的主机记录逐字符比对** ——
  不要凭"应该是指向同一台"的假设。这次是 `81` vs `8`，一眼扫过去并不显眼。
- 验证必需**从外部解析器**问（`@223.5.5.5`），而不是只看本机 `/etc/hosts` 或缓存。
- 证书验证用 `curl --resolve <域名>:443:<真实IP>`：在 DNS 还没生效时也能测通配置，
  并区分「配置错」与「DNS 错」两种失败。

## 教训

基础设施的"已经配好了"和"配对了"是两件事。凡是本次会话里没有亲手 `dig` 过的假设，
都值得在下一次依赖它之前花三秒验证一遍。
