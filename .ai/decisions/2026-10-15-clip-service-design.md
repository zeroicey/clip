# clip 服务设计：后缀寻址、owner token、以及为什么没有构建步骤

**Status:** ✅ ACCEPTED · **Date:** 2026-10-15（拆分后 2026-10-16 重述）
· **Deciders:** 用户（"可以单开一个项目，类似于一个网络剪切板……可以自定义一个路由……
把文本或者图片传过去……这个功能是给人用的，纯前端操作，不需要 AI 操作"）
· **Supersedes:** none · **Related:** `2026-10-16-two-repositories.md`

## 背景

需求：在 `https://clip.hcyj.xyz/<任意后缀>` 打开一块写字板，写下内容保存，
**在另一台机器**的浏览器打开同一个网址即可读到。要能传文本和图片。
典型场景是 Linux 运维：两台机器有网络，但文件不好传、命令不好执行。

这个需求里有几条隐含的约束，它们决定了下面几乎所有裁决：

- **第二台机器可能什么都没有** —— 没有登录态、没有 cookie、可能是个旧浏览器。读必须是匿名的，
  而且不能依赖一个巨大的 SPA。
- **网址要能念出来** —— 后缀短、URL 短，所以才要独占子域名。
- **作者不可信** —— 写入口匿名，所以内容必须按文本渲染，上传必须嗅探。
- **要有兜底** —— 公开匿名写 = 会被滥用，所以限流 + 全局配额 + kill switch 缺一不可。
- **不能有构建产物** —— 这个页面是「随手打开」用的，一条「产物陈旧」的故障链在这里代价过高。

## 裁决

| # | 问题 | 裁决 | 依据 |
| --- | --- | --- | --- |
| D1 | 寻址 | 后缀就是路径的第一段：`/<suffix>`，`^[a-z0-9][a-z0-9_-]{0,31}$`，保留字表拒绝（`api`/`raw`/`favicon`/…） | 短到能从一个屏幕念到另一个；保留字表是硬闸（可写但打不开的后缀等于 bug） |
| D2 | 所有权 | 创建时返回一次 owner token（256 位），服务端只存 `sha256`；改/删必须带 `X-Relay-Clip-Token` | 读匿名是目标，写必须可信；不然「猜后缀 → 改内容」就是个投毒面 |
| D3 | 未知后缀 | **200 + 空编辑器**，不是 404（页面层与 API 层一致） | 第一次访问的**预期动作就是创建**；两者响应体形状相同，不泄漏任何东西 |
| D4 | 过期与接管 | `expires_at` epoch 毫秒，`0` = 永不过期；默认 24h；过期的行**可被新所有者接管**（`ON CONFLICT ... DO UPDATE WHERE expires_at <= now`） | 否则 janitor 还没跑之前，一个没人能读的后缀会永久占位 |
| D5 | 配额 | 事务内 + `pg_advisory_xact_lock` 下检查总量（2 万条 / 1 GiB），超限**拒绝写入并说明** | 「读总量→比较→插入」并发下会一起通过；而且满了要说出来，不能静默丢 |
| D6 | 图片 | 存 `BYTEA`（TOAST），单张 ≤5 MiB、每条 ≤4 张；**类型从字节嗅探**，只允许 PNG/JPEG/GIF/WebP | Postgres 够用，少一个存储系统要备份；SVG 是可执行文档，明确拒 |
| D7 | 实时 | **长轮询 + 单调 `rev`**，`?rev=N&wait=25`；已最新则挂起，被唤醒或超时后返回 | 主交互是「A 存、B 看」的一次跃迁，不是流；不引 WebSocket 的连接生命周期 |
| D8 | 页面形态 | **服务端渲染的单文件 HTML**（`//go:embed page.html`）+ **nonce 内联脚本**；无 JS 时仍可读可复制 | 无构建步骤、无产物陈旧；「另一台机器」上最坏情况也能读。代价是不能编辑（要 JS） |
| D9 | 不引前端工具链 | **删掉 pnpm/Vite/Tailwind/自托管字体**，页面自带极小的内联 CSS | 这一页不值得一条 Node 工具链；代价是与 teleport 面板视觉不共享 |
| D10 | `/raw` | 除页面外提供 `/{suffix}/raw`（`text/plain`）与 `/{suffix}/raw/{n}`（图片） | 运维的另一半时间要的是 `curl <url>/raw`，不是浏览器 |
| D11 | 数据访问 | **sqlc + pgx**，不用 ORM | 所有权判定必须写在 `WHERE` 里；ORM 的糖正是把它藏起来的东西 |
| D12 | 图片上传接口 | `POST /api/clips/{suffix}/assets`（multipart）**整体替换**图片集合，位置即地址 | 部分更新需要第二套寻址（id），而 4 张图全量替换是最便宜的方案 |
| D13 | 封套与命名 | 沿用 `{ok,data,requestId}`；**请求 camelCase、响应 snake_case** | 与 teleport 保持一致，跨语言契约有测试钉住（写错是静默的，见 pitfalls） |
| D14 | 限流键 | `internal/clientip`（立即 peer 是可信代理才采信转发头，从右往左走） | 直接采信 `X-Forwarded-For` = 攻击者每个请求一个新桶 |
| D15 | 部署形态 | 后端跑在 hpcore（本机），公网入口是 hcyj 的 Caddy + **由本机拨出的 frp 隧道** | hcyj → hpcore 的入向 TCP 实测是死的（见 pitfalls） |
| D16 | 可观测 | `/api/health` 返回 `writes_enabled`、条数、字节数；日志只记 method/path/status/bytes/requestId | 配额接近满时要能看见；**绝不记请求头**（token 在 header 里，代理层同理） |

## 后果

**变成前提的**

- 公开匿名写是这个服务唯一的一类新风险面 → 限流、配额、kill switch、noindex、
  以及「后缀是公屏不是密码」这句话必须一直成立。
- 没有构建步骤 → 改页面就是改 `page.html`，一次 `go build` 即生效。**也因此没有「产物陈旧」这类故障。**
- 长轮询是进程内的（`hub.go`）→ 服务必须单实例。现在就是单实例；将来要多实例就得换广播机制。

**已知代价（接受）**

- 只读页面在**没有 JS** 时不能编辑（只能读/复制）。目标场景里读是主要动作。
- 图片进 `BYTEA`：总量超过 ~1 GiB 应改走对象存储。
- 丢掉 localStorage 里的 token = 永久失去那一条的写权限（那是唯一的凭据）。

## 何时重开

1. 图片总量接近 1 GiB → 改走对象存储（本机已有 MinIO，需独立凭据）。
2. 需要多实例 → `hub.go` 的进程内假设与 advisory lock 都要重新设计。
3. 出现真实滥用（配额被刷满、投毒事件）→ 考虑邀请码/登录/只写不改（write-once）。
4. 需要「另一个后缀指向同一份内容」（别名）→ 现在的 `suffix` 是主键，要多一层间接。
