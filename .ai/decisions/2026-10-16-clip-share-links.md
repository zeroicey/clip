# 分享链接：只读的二级路由 + 独立取件口令

**Status:** ✅ ACCEPTED · **Date:** 2026-10-16 · **Deciders:** 用户（分歧一选了「两者都要」；
分歧二/三按其原话“不要把主密码给他”与“别人就只能看”裁定）
· **落地顺序：** 密码先上，分享第二（用户选的）· **Supersedes:** none
· **Related:** `2026-10-16-clip-access-password.md`、`2026-10-16-clip-open-edit-and-ownership.md`

## 背景

用户原话：

> 2 分享权限：如果我想分享给别人 但又不想别人有修改的权限 那我可以再加一个**二级路由**
> （证明这是分享的）后面再跟一个随机的后缀 这样**别人就只能看**。至于分享出去的内容，
> 原本这个 clip 是有密码的，那分享过去还要不要输密码呢？我觉得可以**再设置一个分享密码**。
> （b）分享机制：如果分享出去，可以再设置一个分享密码，**或者给一个 6 位的密码，像快递柜的
> 取件码一样，具有时效性**。

要解决的场景：`clip.hcyj.xyz/我的名字` 是我自己的私有便签（可能带密码）；我想把其中一段内容
给同事看，但**不想给他写权限、也不想把主密码给他**。所以要第二个入口，它：

1. 观感上就能看出「这是分享出去的」（用户明确要求“证明这是分享的”）；
2. **天生只读**；
3. 有自己的口令，和主密码分开；
4. 可以有时效（取件码式），过期即失效。

## 路由形状（`s` 已经是预留后缀）

`internal/clip/suffix.go` 的 `reservedSuffixes` 里 **`s` 与 `k` 已被保留**（当时没写理由），
所以分享路由天然可用 `s`，不需要从用户手里抢名字：

```text
/<后缀>                主人的入口：有密码则要解锁，可读可写（按前一份裁决）
/s/<分享 token>        分享入口：只读；要口令；可带失效时间
/s/<分享 token>/raw    只读的纯文本（给另一台机器的 curl；同样要口令）
```

- `<分享 token>`：服务端生成的高熵短串（例如 16–22 字符 base64url）——**不是**用户选的后缀，
  因为分享链接要能“随手发出去”，而用户自己的名字要留在主入口。
- 分享链接**指向的是同一份内容**（不是拷贝）：主人改了，分享方刷新即见新内容。
  这样“分享的是这个窗口”与主入口的实时同步语义一致，也不需要清理拷贝。
- `/s/…` 必须落在 `reservedSuffixes` 已经挡住的位置（`s` 已挡），且**不受 `ValidateSuffix` 约束**
  （token 是服务端生成的，不走用户输入那条校验）。

## 三个待裁决的分歧

### 分歧一：口令用什么形式

| 选项 | 好处 | 代价 |
| --- | --- | --- |
| **a. 分享密码**（主人自己设，长期有效直到主人撤销/过期） | 主人可控；好记 | 要主人自己想一个；容易到处复用（弱） |
| **b. 6 位取件码**（服务端生成，带时效，快递柜式） | 不用想密码，念给对方就行；符合“临时中转”的定位；过期自动失效 | 空间只有 10⁶ —— **必须**配合短 TTL + 尝试上限，否则可被暴力枚举（后缀本身是公屏语境的短串） |
| **c. 两者都要**（主人选：设一个自定密码，或让服务端发一个取件码） | 覆盖两种场景（“长期给同事看” vs “现在让对方取一次”） | UI 与实现都要做两套；要防“同一条链接两种模式”的歧义 |

**倾向 c**，但分两步落地：先做 a（主人可控、无枚举风险），再按需加 b。

### 分歧二：原 clip 有密码时，分享出去还要不要原密码

| 选项 | 含义 | 评价 |
| --- | --- | --- |
| **a. 分享口令独立**：只知道分享口令就能看，不需要主密码 | 正是用户想要的“不要把主密码给他” | ✅ 推荐（这是这条功能的**存在理由**） |
| b. 要先过主密码、再过分享口令 | 两层锁 | ❌ 功能自相矛盾：那样不如直接把主密码给他 |
| c. 分享链接继承主密码 | 什么都不用设 | ❌ 等于把主密码扩散出去 |

### 分歧三：分享能不能改写 / 能不能撤销

- **只读**这是确定的（用户明确要求）。实现上不是“隐藏按钮”，而是**路由层就没有写入口**：
  `/s/…` 上只挂 GET/HEAD，写形状的请求 405（与刚修好的公共路径方法闸门同一套写法）。
- 撤销：主人可以撤销某个分享（删掉那张分享凭据），撤销后链接立刻失效。默认给一个 TTL。

## 数据模型草案

```sql
-- 一张分享表，一条 share 一张凭据；删行 = 撤销
clips(suffix, body, …, password_hash)                 -- 已有 + 上一份裁决加的一列
clip_shares(
  token        text primary key,   -- 分享链接里的那段（高熵）
  suffix       text not null references clips(suffix) on delete cascade,
  password_hash text,              -- 分享口令（NULL = 只看链接即可看）
  code_hash    text,               -- 取件码（若选 b；与 password 二选一）
  expires_at   bigint not null,    -- epoch 毫秒，沿用全项目约定
  created_at   bigint not null
)
```

- 分享**不复制内容**，所以主人更新正文后分享自动跟着更新。
- `on delete cascade`：clip 过期被 sweep 掉时，分享一起消失（不留悬空链接）。
- 口令同样只存 argon2id 哈希；**同样不能泄漏存在性**（`/s/<token>` 不存在与口令错要形状一致）。

## 安全上必须一起做的

1. **尝试限流**：按 IP **且**按 share token；6 位码那条尤其（否则 10⁶ 很容易枚举完）。
2. **不在 URL 里带口令**：与主密码同一规则（`X-Clip-Password` 头 / unlock 接口），
   因为分享链接会被转发、进聊天记录、进浏览器历史。
3. **Caddy 日志**：若开站点日志，`X-Clip-Password`、`X-Relay-Clip-Token` 都要过滤。
4. **分享链接不能用来枚举后缀**：`/s/<token>` 只认 token，不回显后缀、不泄漏“这个后缀是否存在”。

## 决定

- **路由**：`/s/<分享 token>`（只读）+ `/s/<分享 token>/raw`（只读纯文本）。
  `s` 已在 `reservedSuffixes` 里，不用从用户手里抢名字；token 由服务端生成、高熵、
  **不走 `ValidateSuffix`**（不是用户输入）。
- **分歧一 → c（两者都要）**：主人可以自己设分享密码，也可以让服务端发一个 **6 位取件码**。
  取件码必须配 **短时效 + 尝试上限**（只有 10⁶ 种可能）。
- **分歧二 → a（分享口令独立）**：知道分享口令就能看，**不需要主密码** —— 这正是这个功能
  存在的理由（不要把主密码扩散出去）。
- **分歧三 → 只读 + 可撤销 + 默认 TTL**：`/s/…` 上**只挂 GET/HEAD**，写形状的请求 405
  （路由层就没有写入口，不是“隐藏按钮”）；主人删掉那张分享凭据即撤销；`on delete cascade`
  跟着 clip 一起消失。
- **分享不复制内容**：指向同一份，主人改了分享方刷新即见。

落地前提醒：这份排在密码之后 —— 它要用的四读路径闸门与口令传递方式都是密码那一步建好的。
