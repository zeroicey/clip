## 背景

用户对归属与写权限的原话：

> 忘记密码就不可重试了，只能真正的丢弃。因为我们这里**没有谁是主人、谁是客人**，
> 谁先来占这个位置，那就是谁的，或者说**任何人都可以改它**。
> 比如说，你要是不设密码，所有人打开这个链接都可以改东西。你设置了密码，那这个就是你自己的，
> 因为只有你自己记住。除非你的密码被别人知道了，别人就可以改里面的内容和原本的密码，
> **谁拿到密码谁就是主人**。

这与现状**不同**。现状（2026-10-16 之前的那套）：

- 创建 clip 时服务端生成一个 `owner_token`（明文只回一次，库里只存 sha256）；
- **只有带这个 token 的请求能写**（`X-Relay-Clip-Token`），判定写在 SQL 的 `WHERE` 里；
- 知道后缀的人**能读、不能改** —— 这正是 README 与 `suffix.go` 里
  “a guessed suffix can be read but not defaced” 那句话的由来。

用户描述的模型（= webnote.cc 的模型）里，**token 这个角色被密码取代了**：

| | 无密码 | 有密码 |
| --- | --- | --- |
| 读 | 任何人 | 只有知道密码的人 |
| 写 | **任何人**（用户明确要求） | 只有知道密码的人 |
| 改密码 | 任何人（等于抢注） | 只有知道密码的人 |

## 选项

| 选项 | 好处 | 代价 | 可逆性 |
| --- | --- | --- | --- |
| **A. 完全对齐用户描述**：删掉 token 概念，密码是唯一凭证 | 只有一个凭据概念（页面/文档/心智都简单）；与 webnote 一致；密码无密码两种状态清晰 | **猜到的后缀可以被覆写**（现状不能）；**任何人都能给别人的公开 clip 设密码，把原作者锁在外面**；token 相关代码/测试/契约（`owner_token` 字段、`X-Relay-Clip-Token`、页面 localStorage、跨语言契约测试）都要删或改 | hard（已发出的 token 失效） |
| **B. 保留 token**：无密码时仍只有 token 持有者能写；密码只管有密码的 clip | 保住“猜到后缀不能改”这条现有保证；改动最小 | 两个重叠的凭据概念（token + 密码），用户界面与文档都要解释“为什么我设了密码还……”；与 webnote 不一致 | easy |
| **C. 折中**：无密码 = 任何人可写，但**只有当 clip 还不存在时**才能创建/覆盖？（等于“抢注”放开，但不能改已有公开内容） | 保住了公开 clip 的完整性 | 语义别扭（先来先得只对创建生效），实现与解释都更绕 | medium |

**倾向 A**，理由不是“省事”，而是：用户描述的规则自洽且被明确说出（“谁先来占这个位置，那就是谁的”），
而 B 会让「密码」和「token」两个概念在同一个页面上打架。**但这三件事必须在决定前被看见**：

1. 公开 clip 从「防涂改」变成「可涂改」——这是**能力上的降级**，只是换来了简单；
2. **抢注**：任何人都能对别人的公开后缀设密码，从此原作者也读不到自己的内容；
   用户已接受（“谁先设置密码，这个 clip 就归谁”），但它必须**写进面向用户的文案**，
   否则第一个被抢的人会认为是 bug；
3. 存量：已经在用的浏览器里存有 `owner_token`，删掉 token 后这些一律失效 —— 因为
   无密码的 clip 本来就变成谁都可写，所以**不算数据损失**，但要在发布说明里写一句。

## 决定

**采纳 A。** 这条规则从今天起成立，写成规则而不是偏好：

- **密码是唯一的凭据。** 没有第二把钥匙，也不再发 `owner_token`。
- **无密码的 clip**：任何人都可以读、可以写、可以给它设密码。
- **有密码的 clip**：只有知道密码的人能读、能写、能改密码。
- **谁先设密码谁就是主人**（“谁先来占这个位置，那就是谁的”）。

三条已知代价，用户看过并接受：

1. 公开 clip 从「防涂改」变成「可涂改」；
2. 任何人都能给别人的公开后缀**抢注**一个密码，把原作者锁在外面；
3. 存量浏览器里的 `owner_token` 一律失效（因为无密码的 clip 本来就变成谁都可写，
   **不是数据损失**，但发布说明要写一句）。

### 删什么（同一次改动）

- `clips.owner_token_hash` 列、创建时回传的 `owner_token` 字段、`X-Relay-Clip-Token` 头；
- SQL 里的 `hashOwnerToken(...)` 所有权 `WHERE` 判定（换成密码校验；无密码时不过滤）；
- 页面 `localStorage` 里的 token 逻辑，以及 `TestClientReadsTheFieldNamesTheServerWrites`
  对 `owner_token` 的断言；
- `scripts/verify-clip-browser.cjs` 里所有以 token 为前提的写权限断言（要按新语义重写）。

### 写权限之后的形状

| 谁能写 | 读 | 写 |
| --- | --- | --- |
| 任何人（无密码 clip） | ✅ | ✅（不需要任何凭据） |
| 知道密码的人 | ✅ | ✅ |
| 不知道密码的人 | ❌ | ❌ |

## 后果（若选 A）

- **变容易**：一个凭据概念；页面逻辑（现在有一整套“create 时存 token、之后带着 token 写、
  两个标签页共享 localStorage 会互相踩”的复杂度，见 pitfalls/two-tabs-are-not-two-machines）大幅简化。
- **变难/必须成立**：文案要如实说“公开 clip 谁都能改、谁都可能把它设成私有的”；
  限流策略要重新审视（无密码时写不需要任何凭据，滥用面变大——现在至少还有一个 token 挡着）。
- **要重测**：`scripts/verify-clip-browser.cjs` 的写权限断言（“the owner can update over the API”等）
  全部要按新语义重写。

## 何时重开

- 真出现公开 clip 被恶意涂改/抢注 → 回到 B（token）或引入“创建者签名”。
